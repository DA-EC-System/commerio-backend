# db/

Migration của PostgreSQL. Một database, **mỗi module lớn một schema cùng tên**: `core`, `product`, `order`, `finance`, `channel`, `insight` (`Documents/19` D1; `notification` không có bảng). Module con khai bảng trong `src/modules/<lớn>/<con>/repository/schema.ts` với `pgSchema('<lớn>')`. Thiết kế từng bảng: `Documents/19-mo-hinh-du-lieu.md` mục 3.

**`order` là từ khoá SQL**: SQL viết tay phải ghi `"order".orders`, không ghi `order.orders` (Drizzle tự thêm ngoặc kép).

## Tài liệu schema và phiên bản

Ba thứ **sinh tự động, không sửa tay** (`npm run db:docs`; `db:generate`, `db:regen` tự chạy), nguồn là snapshot của migration mới nhất, comment trong `schema.ts`, khoá ngoại, trigger, index, EXCLUDE viết tay trong migration (`scripts/db/lib/sql-objects.ts`, đọc câu SQL tĩnh; SQL động trong `DO $$ … $$` như vòng lặp RLS của 0002 không đọc). Không có: RLS, policy, quyền, hàm SQL:

| File | Nội dung |
|---|---|
| `SCHEMA.md` | Mục lục: phiên bản hiện tại, mọi bảng theo schema kèm câu mô tả đầu, mục **Đã bỏ** |
| `schema/<schema>.md` | Từng bảng: mô tả, file khai báo, cột (kiểu, null, mặc định, giá trị enum, trỏ tới đâu, comment), ràng buộc, index, bảng nào trỏ vào |
| `VERSIONS.md` | Mỗi migration một phiên bản `V<n>`, mới nhất trước: ngày, sinh hay viết tay, bảng, cột, ràng buộc, enum đã đổi |

- **Đọc `SCHEMA.md` và `schema/<schema>.md` trước khi thêm bảng, cột, enum.** Đã có thứ cùng nghĩa thì dùng lại.
- **Phiên bản `V<n>`** = migration thứ n trong `meta/_journal.json` (`versionLabel`). Journal của `main` chỉ thêm vào cuối nên số không đổi sau khi merge; migration của nhánh mang số tạm. Tên file migration giữ nguyên cách đặt theo giờ (số V không nằm trong tên file). `db:migrate:check` in phiên bản của DB và của mã nguồn.
- **Đã bỏ**: thêm thẻ `@deprecated <lý do>` vào JSDoc của bảng hay cột trong `schema.ts` (IDE cũng gạch chỗ dùng). Xoá hẳn bảng, cột thì bỏ thẻ cùng lúc.
- **Cột uuid tên `*_id` không có khoá ngoại** (trỏ sang schema khác, module con khác): khai bảng đích ở `LOGICAL_REFS`, hoặc lý do không trỏ bảng cố định ở `NOT_REFS` (`scripts/db/lib/schema-refs.ts`). Tên theo quy ước `<bảng số ít>_id` khai theo tên cột; tên mang nghĩa riêng khai theo `<schema>.<bảng>.<cột>`. Chưa khai, hoặc mục khai không còn khớp cột nào, thì `db:docs` báo lỗi. Cột `*_by` (người thao tác → `core.accounts`) và `company_id` không cần khai.
- `db:ci-check` và `test/unit/db/docs.test.ts` đỏ khi ba thứ trên chưa ghi lại hoặc có cột chưa khai. Sửa comment `schema.ts` mà không sinh migration thì chạy `npm run db:docs`.
- Gộp main bị xung đột ở `SCHEMA.md`, `schema/`, `VERSIONS.md`: để nguyên, `npm run db:regen` ghi lại (nhánh không có migration thì `npm run db:docs`).
- **ERD tương tác**: `npm run db:erd` dựng từ cùng mô hình (`scripts/db/lib/erd.ts`, bố cục bằng `elkjs`, trang `scripts/db/erd/page.html`), ghi `.erd/commerio-erd.html` (không commit) rồi mở trình duyệt; `-- --no-open` chỉ ghi file. Có tổng quan 6 schema, sơ đồ từng module (cột khoá hoặc mọi cột), quan hệ trực tiếp của một bảng, chi tiết cột và ràng buộc, phiên bản `V<n>` ở đầu trang. Có migration mới: `git pull` rồi chạy lại.

## Migration

- **Không để hai migration sinh từ `schema.ts` liền nhau trong một PR** (`db:ci-check` xếp loại theo snapshot: migration viết tay có snapshot giống migration trước). Sinh, sửa schema, sinh tiếp thì `npm run db:regen` gộp thành một. Hai migration sinh có migration viết tay ở giữa thì được, cho kiểu thêm cột → chép dữ liệu → bỏ cột cũ hay siết ràng buộc. Lưu ý: `db:regen` (khi phải sinh lại sau khi gộp main) vẫn gộp mọi migration sinh và dời migration viết tay ở giữa ra sau, lệnh cảnh báo; khi đó viết câu dữ liệu vào giữa file sinh gộp, hoặc tách thành hai PR.

- Thứ Drizzle không sinh được (RLS, extension, trigger, EXCLUDE): `npm run db:generate -- --custom --name <mo-ta>` tạo file SQL trống rồi viết tay; dòng comment `--` đầu file là câu tóm tắt hiện ở `VERSIONS.md`. Bảng thêm sau **phải tự bật RLS** trong migration `--custom` (vòng lặp của 0002 chỉ chạy một lần).
- **Thêm giá trị enum** (`ALTER TYPE … ADD VALUE`, drizzle sinh từ `schema.ts`): PostgreSQL không cho dùng giá trị mới trong chính giao dịch thêm nó, mà migrator chạy mọi migration đang chờ trong **một** giao dịch, nên không migration nào (kể cả file khác cùng PR hay cùng lượt deploy) được ghi giá trị đó. Dữ liệu cũ thì để code nhận cả hai dạng, hoặc chuyển ở lần deploy sau. Không lùi được (không có `DROP VALUE`); giá trị thừa vô hại khi lùi code. Ví dụ: `*_mo-kien-kiem-ke` (`open_purpose = 'stocktake'`, #238 PR 2).
- **Khoá ngoại ghép trỏ unique ghép** (vd `pavi_product_fk` → `products(id, image_attribute_id)`, #340): drizzle-kit sinh câu `FOREIGN KEY` **trước** câu `UNIQUE` đích nên migration lỗi `there is no unique constraint matching given keys`. Khai hai `unique()` đích trong `schema.ts`, viết khoá ngoại trong migration `--custom` (cùng file với RLS của bảng), ghi chú trong `schema.ts` trỏ tới migration đó; `db:regen` chép nguyên migration viết tay ra sau nên vẫn đúng thứ tự. Ví dụ: `*_anh-phan-loai-rls`.
- Index **biểu thức** cần `NULLS NOT DISTINCT` (vd `(company_id, lower(name))` với vai trò có sẵn `company_id` trống) Drizzle không sinh được: viết trong migration `--custom`, không khai trong `schema.ts` để `db:generate` sau này không đòi xoá; ghi chú trong `schema.ts` trỏ tới migration đó.
- Staging là PostgreSQL 17 trên Supabase, chạy migration bằng user không phải superuser. Không dùng tính năng chỉ có ở PG18 (`uuidv7()`, cột ảo). Test integration đã chạy migration bằng role `NOSUPERUSER CREATEROLE` cho giống; thử trên PG17: `TEST_PG_IMAGE=pgvector/pgvector:pg17 npx vitest run --project integration`.

## Ràng buộc nghiệp vụ trong DB

- Bảng có bước duyệt dùng cột chung `approval` (`created_by`, `approved_by`, `approved_at`, `self_approved`) và CHECK `approvalCheck` (`src/shared/db/columns.ts`): người duyệt khác người lập, trừ khi `self_approved` (CEO, hoặc công ty một người; service quyết). Người thứ hai giữa hai cột khác (COD, thất lạc, kết quả trả NCC, chốt lệch) là CHECK riêng của bảng.
- Thất lạc của kiện (#238, migration `*_that-lac-cot`, `*_that-lac-du-lieu`, `*_that-lac-rang-buoc`): `packages_lost_second_person` (người xác nhận khác người báo, trừ `lost_self_approved`), `packages_lost_source` (`user`, `marketplace`), `packages_lost_confirmed` (kiện `lost` phải có `lost_source = 'marketplace'` hoặc `lost_confirmed_by`). CHECK so cột có thể null dùng `is not distinct from`: `=` với null ra NULL và CHECK cho qua.
- Trạng thái kéo theo cột bắt buộc (đã ghi sổ thì có `posted_at`, hoàn tiền NCC thì có số tiền…) là CHECK. Quy tắc trải nhiều bảng (`đạt + lỗi ≤ còn chờ`, người ghi sổ phiếu nhận khác người lập đề nghị) do service kiểm.
- Tồn: `stock_levels_invariant` cho phép tồn thực âm hoặc nhỏ hơn đang giữ **chỉ khi** bật `invariant_broken` (hai ngoại lệ của `25` §7.1).
- Dòng kiện, kiểm bằng (#205; migration `*_huy-dong-kiem-bang` thay trigger chặn vượt của `*_tach-kien-bat-bien`): với một dòng đơn, tổng `quantity − pending_drop_qty` trên các kiện chưa huỷ **bằng** `order_lines.quantity − cancelled_qty`. Hàm chung `"order".assert_package_line_total(line_id, require_lines)`, ba constraint trigger `DEFERRABLE INITIALLY DEFERRED` (kiểm lúc commit):
  - `package_lines_line_total` trên `package_lines` (`INSERT`, `DELETE`, `UPDATE OF quantity, package_id, order_line_id, pending_drop_qty`): luôn kiểm, nên xoá dòng kiện cuối mà không ghi `cancelled_qty` cũng bị chặn.
  - `packages_line_total` trên `packages` (`UPDATE OF status`), chỉ khi trạng thái qua lại ranh giới `cancelled` (`WHEN`, spec 205 D19): kiểm mọi dòng đơn của kiện.
  - `order_lines_line_total` trên `order_lines` (`UPDATE OF quantity, cancelled_qty`), chỉ khi giá trị đổi (`WHEN`); dòng đơn chưa có dòng kiện nào thì bỏ qua (món trạng thái lạ, nhóm bỏ qua vì `resplit`). Không gắn vào `INSERT` của `order_lines`.
  - Dòng kiện trỏ tới dòng đơn không có thì bỏ qua. Hàm chạy quyền người gọi và **không khoá** dòng đơn (tránh vòng khoá với luồng nhận đơn), nên đường ghi dòng kiện, đổi chờ bỏ, huỷ kiện phải khoá kiện trước. Lỗi `23514` kèm `constraint = package_lines_line_total` cho cả ba; muốn báo ngay trong giao dịch thì `set constraints "order".package_lines_line_total immediate`.
  - Seed, test chèn kiện `cancelled` có dòng phải ghi `cancelled_qty = quantity` cho dòng đơn trước (`seedPackage` đã làm); đổi chờ bỏ hay `cancelled_qty` bằng SQL tay thì đổi cả hai trong một giao dịch.
  - `*_huy-dong-du-lieu` (viết tay, chỉ dữ liệu, chạy lại được): dòng đơn chỉ còn nằm trong kiện đã huỷ thì `cancelled_qty = quantity`; đơn `unpaid`, `processing` mà `raw_orders.payload.lines` có món `cancelled` thì đặt `external_update_time = 'epoch'` và xoá `last_order_sync_at` của gian hàng để lượt kéo sau áp luật huỷ dòng (D22). Không đặt NULL như 0022: `findRawOrderTimes` bỏ dòng NULL nên đơn đặt trước mốc kéo đơn sẽ bị lọc mãi; `epoch` vẫn là "đơn đã có" và cũ hơn mọi lần sàn sửa. Worker cũ còn chạy lúc đổi image thì chạy lại hai câu `UPDATE channel…` sau rollout.

## Row-Level Security

Bảng thuộc công ty có `company_id` và chính sách `company_isolation`: chỉ thấy dòng có `company_id = current_setting('app.company_id')`.

- **Request trong một công ty:** transaction chạy `SET LOCAL ROLE commerio_app` và `set_config('app.company_id', <id>, true)`. Role này không phải chủ bảng nên RLS có hiệu lực; chưa đặt `app.company_id` thì không thấy dòng nào.
- **Luồng không thuộc công ty nào** (đăng ký, đăng nhập, chọn công ty, quản trị nền tảng, worker): chạy bằng role đăng nhập, là chủ bảng nên bỏ qua RLS. Vì vậy không bật `FORCE ROW LEVEL SECURITY`.
- Bảng mới tạo bằng migration tự cấp quyền cho `commerio_app` (`ALTER DEFAULT PRIVILEGES` của 0002), nhưng **phải tự viết** `ENABLE ROW LEVEL SECURITY` và policy trong một migration `--custom`.
- Bảng chung không có RLS: `core.companies`, `core.accounts`, `core.permissions`, `core.refresh_tokens` (chỉ luồng xác thực đọc). Trong công ty, `core.accounts` chỉ đọc và thêm. Vai trò có sẵn (`company_id` trống) công ty nào cũng đọc được nhưng không sửa, không xoá được, kể cả quyền của nó (0002).

- `test/integration/shared/rls-coverage.test.ts` quét mọi bảng: bảng có `company_id` thiếu RLS/policy, hay quyền của `commerio_app` khác mong đợi, là đỏ. Bảng cố ý khác thì thêm vào `RLS_EXCEPTIONS`/`EXPECTED_PRIVILEGES` trong file đó kèm lý do.

## Hai nhánh cùng sinh migration: người merge sau **bắt buộc** sinh lại

Migrator của drizzle-orm (`drizzle-orm/pg-core/dialect.js`, hàm `migrate`; `drizzle-kit migrate` dùng chung) đọc dòng mới nhất của `drizzle.__drizzle_migrations` (`order by created_at desc limit 1`) rồi chỉ chạy migration có `when` (trong `meta/_journal.json`) **lớn hơn** `created_at` của dòng đó, mọi migration đang chờ trong **một** giao dịch. Migration sinh trên nhánh khác trước nhưng merge sau sẽ bị **bỏ qua im lặng** trên DB đã có dữ liệu (staging), trong khi test (DB trống) vẫn xanh. Tên file theo thời điểm sinh **không** chữa được: nó chỉ hết trùng tên file, còn thứ tự chạy vẫn theo `when`, và snapshot của hai nhánh vẫn cùng nối vào một snapshot cha.

Ba lớp chặn (`scripts/db/`):

| Lệnh | Chạy ở | Chặn gì |
|---|---|---|
| `npm run db:ci-check` | Job `static` của CI ở mọi PR (`-- --base origin/main`), không cần DB | Migration của nhánh không đứng sau migration mới nhất của main (`when` và tên); nhánh sửa file `.sql` đã có trên main; journal đứt `idx`, `when` không tăng; file `.sql` hay snapshot không có trong journal; snapshot trỏ sai cha (`prevId` khác `id` của snapshot liền trước); `drizzle-kit generate` (chạy trên bản sao trong thư mục tạm) còn sinh ra file, tức `schema.ts` và migration lệch nhau; nhánh có hai migration sinh từ schema liền nhau; tài liệu schema chưa ghi lại hoặc có cột uuid `*_id` chưa khai bảng đích |
| `npm run db:migrate` (`:staging`) | Job `migrate` của deploy staging, job `blackbox` của CI, máy dev | Thay `drizzle-kit migrate`. So journal với `drizzle.__drizzle_migrations` (đã chạy khi và chỉ khi có dòng `created_at` = `when`, như drizzle; hash chỉ để cảnh báo); có migration chưa chạy mà `when` ≤ dòng mới nhất, hoặc có dòng `created_at` NULL, thì **dừng, mã lỗi 1, in tên file, không chạy gì**; không thì chạy migrator của drizzle-orm như cũ, xong kiểm lại không còn sót. Giữ khoá advisory `commerio:db-migrate` trong lúc chạy |
| `npm run db:migrate:check` (`:staging`) | Tay | Chỉ đọc (giao dịch `READ ONLY`, không tạo bảng): phiên bản `V<n>` của DB và của mã nguồn, liệt kê đã chạy, chưa chạy, lệch thứ tự, dòng trên DB không khớp journal, file `.sql` khác bản đã chạy. Mã lỗi 1 nếu có lệch thứ tự |

**Sinh lại bằng `npm run db:regen`** (sau khi `git merge origin/main` và giải xung đột `schema.ts`; xung đột `_journal.json` để nguyên): lấy `_journal.json` của `origin/main` (`--base <ref>` để đổi), xoá migration của nhánh (file `.sql` và snapshot không có trên main), chạy `drizzle-kit generate --name <slug cũ>` một lần cho mọi migration sinh từ schema, rồi chép nguyên nội dung từng migration viết tay (snapshot giống hệt snapshot cha: RLS, quyền, dữ liệu) vào migration `--custom` mới cùng slug, cuối cùng ghi lại tài liệu schema (số `V<n>` của nhánh đổi theo). Xung đột ở `SCHEMA.md`, `schema/`, `VERSIONS.md` cũng để nguyên. `--dry-run` chỉ in kế hoạch. Giới hạn:
- Nhiều migration sinh từ schema gộp thành một (tên ghép các slug): không có `schema.ts` của từng bước để sinh riêng. Viết tay đứng trước migration sinh đầu tiên vẫn đứng trước; viết tay đứng giữa hai migration sinh bị dời ra sau migration gộp, lệnh cảnh báo để kiểm lại.
- Câu lệnh viết tay thêm vào migration sinh bị mất khi sinh lại: lệnh so câu lệnh cũ với bản mới, in câu thiếu và trả mã 1 để chép tay.
- drizzle-kit hỏi đổi tên cột/bảng thì trả lời như khi `db:generate`.

**Action tự sinh lại** (`.github/workflows/migration-regen.yml`, script ở `scripts/ci/migration-regen/`): mỗi lần push vào `main` có đổi `db/migrations/`, với mọi PR mở vào `main` (cùng repo, không có nhãn `no-auto-regen`, chưa chứa `main`, có tệp `db/migrations/`), Action gộp `main` vào nhánh, xung đột chỉ ở `db/migrations/`, `db/SCHEMA.md`, `db/schema/*.md`, `db/VERSIONS.md` thì lấy bản `main`, chạy `db:regen -- --non-interactive` rồi `db:ci-check -- --base origin/main`; đạt thì đẩy hai commit (merge, sinh lại) lên nhánh, `git pull` trước khi làm tiếp. Không đẩy, chỉ để một bình luận (sửa đè mỗi lần) vào PR khi: xung đột ở tệp khác (vd `schema.ts`), drizzle-kit hỏi đổi tên cột/bảng (không bao giờ tự trả lời), `db:regen` cảnh báo (mất câu viết tay), `db:ci-check` đỏ, hoặc nhánh vừa có commit mới. Khi đó làm tay như trên. Chạy lại cho một PR: tab Actions → Migration regen → Run workflow, nhập số PR. Nhánh đang dựng tay (gom chuyến) thì gắn nhãn `no-auto-regen`.

### Migration bị bỏ sót trên DB đã có dữ liệu

`db:migrate` dừng và `db:migrate:check` liệt kê ở mục "Lệch thứ tự". Không có lệnh tự sửa. Với migration đã ở main: chạy tay nội dung file trên DB đó, rồi ghi dòng `insert into drizzle.__drizzle_migrations (hash, created_at) values ('<sha256 của file .sql>', <when>)` (hash: `node -e "console.log(require('crypto').createHash('sha256').update(require('fs').readFileSync('db/migrations/<tag>.sql')).digest('hex'))"`), chạy lại `db:migrate:check` thấy hết lệch. **`created_at` là cột bắt buộc** khi chèn tay: dòng thiếu nó bị drizzle coi là mới nhất (`order by created_at desc` xếp NULL lên đầu), đổi thành 0 và chạy lại mọi migration; `db:migrate` dừng khi gặp dòng như vậy.

DB local (máy dev) bị chặn vì từng chạy migration của nhánh khác, hoặc cảnh báo "trùng nội dung một migration đã chạy dưới tên khác" sau `db:regen`: xoá DB rồi `npm run db:migrate` lại.

`test/unit/db/journal.test.ts` đỏ nếu `when` không tăng theo `idx`, hoặc tên file không khớp `when`.

Seed dữ liệu demo (dữ liệu giả, không dùng thông tin khách hàng thật) đặt ở `db/seed/`, chạy bằng `npm run db:seed` (`db/seed/index.ts`, #37).
